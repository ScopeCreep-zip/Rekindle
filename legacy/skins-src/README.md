# Xfire skin source archives

The original download archives of every Xfire skin that still survives, one zip per distinct skin, stored
byte-for-byte as downloaded on 2026-11-26. They are the inputs for converting every skin to the shared secure
`.rkskin` format (plan step E7.7, `design-skin-catalogue-2026-11-26.md` rulings 1, 2 and 6; census
`census-xfire-skins-2026-11-26.md`).

- **One zip per skin.** Archives were deduplicated by the importer's **tree hash**
  (`rekindle_skin::import::tree_hash` over xtask's `read_tree` walk of the skin root, defined in
  `legacy/skins/README.md`). Where several archives hold the same tree, the stored one comes from the most
  authoritative source: Xfire's own media host (via the Wayback Machine) first, then the archive.org item
  `XFireSkins`, then the Xf1re library. A source marked "other bytes, same skin" holds the same tree (or the same skin
  double-packed) in a differently packed zip.
- **Skin root.** The directory holding `Info.xml` + `Skin.xml` (XML era) or `version.ini` (INI era); CS-Source and Waste
  are INI era without a `version.ini`, rooted at the folder holding `<folder>.ini` with `[MainWindow]`. Two stored zips
  hold the skin twice (`worldofwarcraft`, `xfire-classic`: the skin plus a nested copy in a subfolder); both tree hashes
  are listed. `xfire-classic.zip` (Xfire's own file) names its copy with a parent prefix: 447 entries start with
  `../installer/skins/xfire/`. Unpacked with `..` components dropped, so nothing lands outside the target (the census
  rule, and how `legacy/skins/xfire-classic/xfire/` was made), the whole tree is `ccb37e23...` and the copy at
  `installer/skins/xfire/` is the same skin as the top level, `acf8c359...`. No other zip here has a `..` entry. Xf1re's `bionical` and `symbiosis` zips are double-packed the same way, but archive.org's zip of the inner
  tree is the one stored; the outer tree's hash is listed as "not stored".
- **Verified.** Every zip here was unpacked into a scratch directory and its tree hash(es) recomputed with the
  importer's hash; each equals the hash in its row.
- **Credit line** is copied from the skin's own metadata: `Info.xml`'s `<Author Type=...>` and `<Website>` elements
  (XML era) or the non-key lines of `version.ini` with the `;` comment marker dropped (INI era). An empty cell means
  the file names no author.
- **Import status** is a dry run of today's importer (`xtask import-skin`, release build at `9026d6cb7`) on the stored
  tree, no `--credit-*` flags.
- **Ships** says whether Rekindle ships the skin today as a built-in pack. The ten whose tree equals a built-in's
  verified tree are also stored unpacked in `legacy/skins/`; the zip here is the original download artifact of that same
  tree. `xslimfire`'s zip is the author's original; the built-in uses the corrected tree in `legacy/skins/xslimfire/`.

The art, sounds and palettes are their authors' work (Xfire, Inc. and community skin authors). Rekindle's MIT licence
does not cover them; each converted pack carries a NOTICE crediting its authors.

## Moving-sibling anchors (SKC4, ruling 5)

Three tiles stretch from the far edge of a **centred** sibling to their parent's far side, and the importer has no span
for that today (`skin_tree/anchor.rs:422-427`, the `Pos::Ref(At::Centre(_))` arm of a `Resize*=100` tile). Both packs
fail with that exact error, so neither ships half-imported:

| Pack | Tile | Exact error |
|---|---|---|
| `bionical` (both trees) | `Rightlines` (`biochat.ini:118-124`, `bioGroupChat.ini:127`) | `skin tree: Rightlines: skin tree: X: ax stretch from an edge and ax far side` |
| `nvidia-reactor` | `RightResizeBot` (`nVidiaChatSkin.ini:92-97`, `nVidiaGroupChatSkin.ini:92-97`) | `skin tree: RightResizeBot: skin tree: Y: ax stretch from an edge and ax far side` |

**Evidence that Xfire laid them as a span from the moving edge to the far side.** The DTD (`xfireskin.dtd:79-89`)
declares `X`, `ResizeX`, `Indent*` and `Just*` as bare `CDATA`, so the behaviour comes from the packs themselves (gfire
and OpenFire implement Xfire's network protocol, not its skin engine, so they hold nothing on layout):

- Bionical's chat lays its send button centred (`Window42.Name=SendButton` `JustX=CENTER JustY=BOTTOM`,
  `biochat.ini:113-116`) with a line graphic on each side: `Leftlines` `X=-21 ResizeX=50` (`:126-131`), a box from the
  left edge that grows by half the window's growth, so its far end tracks the centre where the button sits; and
  `Rightlines` `X=SendButton.RIGHT ResizeX=100 IndentRight=20` (`:118-124`), whose art `RLGraphic` is centred in it
  (`JustX=CENTER`, `:353-365`). The pair flanks the button at every width only if `Rightlines` runs from the button's
  right edge (moving at half the window's rate) to 20 px short of the right edge; a box that kept the button's start
  and also grew by the whole window's growth would run past the window.
- nvidia[Reactor]'s chat splits its right resize edge around the vertically centred info button
  (`InfoViewButtonBg` `JustX=RIGHT JustY=CENTER`, `nVidiaChatSkin.ini:56-59`): `RightResize` `ResizeY=43` from the
  top (`:85-88`), about half the height, and `RightResizeBot` `Y=InfoViewButtonBg.BOTTOM Y=-10 ResizeY=100`
  (`:92-97`, `Action.lbtndown=ResizeR`, `:326-330`) from the button down to the bottom edge. Again the grip only
  covers the edge below the button if it spans from the button's moving bottom to the far side.

So the evidence shows Xfire laid this form, as it lays the start-anchored case (`X=TabNormalButton.RIGHT+12
ResizeX=100`, `anchor.rs` `from_far`). The span it needs is: start at the centred sibling's far edge (Xfire floors the
centre, `Anchor::Centre`), end at the parent's far edge less `Indent*`. No current `NodeSpan` holds a start that moves
with the centre, so it is a new span form in `rekindle-types` with its Host stylesheet and box rules; it is owed to the
next slice (SKC4 stopped at its call budget), and the two packs stay listed here until it lands.
